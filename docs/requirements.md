## 1. プロジェクト概要

### 1.1 プロジェクト名

Personal AI Secretary

### 1.2 目的

利用者の自己管理にかかる認知的負担をAIが引き受け、目標・予定・タスク・日々の状態をもとに、無理のない計画を作成・調整する。

本システムは、利用者自身を「計画的な人間に変える」ことを目的とせず、計画を立てる・優先順位を決める・予定を修正する・空き時間の使い方を考えるといった自己管理の負担を軽減することを目的とする。

### 1.3 基本思想

- 利用者の意思を尊重する
- AIが必要な判断を代行する
- 利用者への入力要求を最小限にする
- 毎日を最大効率で埋めるのではなく、余白を確保する
- 利用者のその日の気分・疲労度・集中状態を計画に反映する
- 予定変更が発生しても簡単に再計画できるようにする
- 利用者の確認なしに目標やスケジュールを確定しない

### 1.4 コア価値

「何をするか」「いつするか」「どれくらいやるか」「今日は休むべきか」「空き時間をどう使うか」「予定が崩れたときどうするか」といった判断をAIが支援し、利用者は重要な意思決定だけに集中できるようにする。

最終的には、**「自分で自分を管理する」のではなく、「AIに自己管理を支援してもらいながら、自分のやりたいことに集中できる状態」**を実現する。

---

## 2. 解決したい課題

単純に「タスクを忘れる」ことだけが問題ではなく、以下の複数の認知的負担が存在する。

- タスクを登録する負担
- タスクの優先順位を決める負担
- いつやるかを決める負担
- 空き時間に何をするか考える負担
- 予定変更後に計画を作り直す負担
- 締切のないタスクを継続する負担
- 予定を詰め込みすぎないよう調整する負担
- 疲労や気分に応じて予定を変更する負担
- 移動時間を見込んで予定を組む負担

本システムでは「タスク管理」だけではなく、「自己管理に伴う意思決定そのもの」を支援対象とする。

| 項目 | 内容 |
|---|---|
| 対象ユーザー | 授業・課題・就活・アルバイト・資格勉強などを並行する大学生 |

## 4. MVPの範囲

### 4.1 前提

- 開発人数：3人（2人の場合の分担はタスク細分化を参照）
- 実装期間：3日間
- 実装開始前にモック（画面と遷移の大枠）を完成させておく
- MVPの目的は機能を大量に作ることではなく、Demo Path を3日間で通すこと

### 4.2 Demo Path

```text
① ログイン
② 目標を相談（Interview AIが質問）
③ 目標時間3案を提示
④ ユーザーが選択・調整して確定
⑤ 「スケジュール作成」を押す
⑥ Planning Engine が今週のスケジュール3案を生成
⑦ ユーザーが1案を選択
⑧ 今日の予定を表示
⑨ 「今日は疲れた」と伝える
⑩ AIが再計画
⑪ 変更前後を確認して確定
（＋）月・週・日のカレンダーで計画を確認
```

以下が1回の操作で通ればMVP完成とする。

### 4.3 優先度

| 優先度 | 機能 |
|---|---|
| **S：必須** | Interview AI / 目標時間3候補 / Goal Handoff / Planning Engine / バッファ / スケジュール3案 / 今日のタイムライン |
| **A：できればMVPに入れる** | 再計画（Demo Pathの⑨〜⑪） / カレンダー表示（月・週・日、閲覧のみ） / 場所と移動時間 / 固定予定の登録 / タスクの登録・編集 / デイリーチェックイン |
| **B：後回し** | 週間レビュー / 月間レビュー / Google Calendar連携 / 自然言語によるタスク登録 / 高度なパーソナライズ（修正内容の学習） / アルバイトシフト管理 |
| **C：3日ではやらない** | 完全自動化 / 高度な長期学習 / 複雑な推薦 / Google Calendarの完全同期 / 高度な分析ダッシュボード / 地図APIによる移動時間の自動計算 |

優先度Aのうち「固定予定」「場所と移動時間」「タスク」は、登録画面を作らない場合でも、デモ用のseedデータとして必ず用意する。Planning Engine の入力として必要なためである。

## 5. システム構成と責務分担

### 5.1 技術スタック

| 役割 | 使うもの |
|---|---|
| フレームワーク | Next.js（App Router）＋ TypeScript |
| データ検証 | Zod |
| UI | Tailwind CSS ＋ shadcn/ui（Base UI版） |
| DB・認証 | Supabase（クラウド） |
| LLM | OpenAI API（サーバー側のみから呼ぶ） |
| デプロイ | Vercel |

### 5.2 責務分担

| 担当 | 責務 | やってはいけないこと |
|---|---|---|
| LLM | 自然言語の理解、情報抽出、気分・状態の理解、候補と計画の説明、再計画要求の意図抽出 | 最終的なスケジュールの時間配置、固定予定・締切・目標の変更 |
| Planning Engine | 優先度計算、空き時間計算、移動時間の確保、バッファ確保、タスク割り当て、3案生成、妥当性検証、再計画の配置 | LLMへの配置の丸投げ |
| DB / API | 状態とデータの正規化・永続化、認証、利用者ごとのデータ分離 | クライアントから送られた user_id をそのまま信頼すること |
| Frontend | 利用者が「選ぶ・確認する・変更する」ためのUI | 利用者の操作なしに生成・確定を進めること |

AIに最終的なスケジュールを自由生成させない。AIは「理解・解釈・説明」を担当し、最終的な計画生成はルールベースの Planning Engine が担当する。

## 6. 機能要件

各機能に ID を振る。Issue・PR・コミットメッセージではこの ID を参照する。

### 6.1 認証（F-01） 優先度S

- 利用者はメールアドレス等でログインできる
- 認証済みの利用者のみ自分のデータを取得・変更できる
- モック段階では「ログイン」ボタンを押すだけで次へ進む仮実装とする

**受け入れ条件**：未ログインでは各画面・APIにアクセスできない。他の利用者のデータは取得できない。

### 6.2 ヒアリング（Interview AI）（F-02） 優先度S

ヒアリングAIは、情報を一度に大量に取得するのではなく、自己管理に必要な意思決定を段階的に支援する。目的は「何をしたいか」→「どの程度やりたいか」→「本人が納得した目標を確定する」までの認知的負担をAIが引き受けることである。

#### 6.2.1 対話ステップ

| # | ステップ | 内容 |
|---|---|---|
| 1 | category | 今一番力を入れたいことのカテゴリ（資格・テスト勉強／筋トレ・運動／大学の課題・レポート／就活／その他） |
| 2 | goal | 目標 |
| 3 | current_status | 現在の状況・経験・レベル |
| 4 | conditions | 期限・条件・制約 |
| 5 | time_estimation | 必要な目標時間を考える材料の確認 |
| 6 | goal_candidates | 目標時間3候補の提示 |
| 7 | user_selection | 利用者が選択または微調整 |
| 8 | summary | 確定した目標の要約 |
| 9 | final_confirmation | 利用者に最終確認 |

一度の発話では原則1〜2問までとし、回答内容に応じて次の質問を動的に決定する。回答の手間を減らすため、選択肢で答えられる質問には候補ボタン（クイックリプライ）を表示する。

#### 6.2.2 大学生向けの制約の取得

必要に応じて授業、課題、試験、就活、アルバイト、サークル、通学、睡眠、友人・家族との予定等を取得する。ただし初回からすべてを質問せず、目標設定に必要な情報だけを先に取得する。固定予定・場所・移動時間は、ヒアリングではなく登録済みデータ（MVPではseedデータ）から取得する。

#### 6.2.3 ヒアリング完了条件

以下が確定した時点で基本的なヒアリングを完了する。

1. タスク名・目標
2. 目標時間または頻度
3. 期限・条件

不足情報がある場合のみ追加質問する。

#### 6.2.4 最終確認の表示

ヒアリング完了後、AIは勝手に曜日・時間帯のスケジュールを作成してはならない。必ず以下の形式で最終確認を提示する。

```text
目標の整理が完了しました！👍

📚 今週の目標データ
・[タスク名1]：[目標時間/頻度]（[補足条件や期限]）
・[タスク名2]：[目標時間/頻度]（[補足条件や期限]）

⏱️ 今週の合計目標時間：◯時間

この条件を元に、あなたの生活リズムや固定予定に合わせた
おすすめのスケジュールプランを3つ作成します！

準備ができたら「スケジュール作成」を押してください。
```

#### 6.2.5 状態遷移

```text
INTERVIEWING → CONFIRMING → COMPLETED → READY_FOR_PLANNING
READY_FOR_PLANNING →（「スケジュール作成」操作）→ PLANNING → PLAN_PROPOSED
```

- `COMPLETED` または `READY_FOR_PLANNING` から、利用者の明示的な「スケジュール作成」操作なしに `PLANNING` へ遷移してはならない
- 不正な遷移はエラーとする
- 状態はDBとAPIで一貫させる

#### 6.2.6 UX上の禁止事項

- 一度に大量の質問をしない
- 分からない情報を無理に回答させない
- 目標時間をAIが一方的に決定しない
- 候補の1つを正解として押し付けない
- ヒアリング完了後に勝手に予定を配置しない
- 利用者の承認なしに目標を変更しない
- 不明な期限・時間・予定を推測しない
- 効率だけを理由に利用者の希望を無視しない

**受け入れ条件**：会話から正規化された目標が取得でき、「スケジュール作成」を押すまでスケジュールが生成されない。

### 6.3 目標時間3候補（F-03） 優先度S

利用者が必要量を判断できない場合、AIは状況から3候補を生成する。

| 内部名 | 表示名 | 初期目安 |
|---|---|---|
| `intensive` | 短期集中型 | 基準値 × 1.5 |
| `balanced` | バランス標準型 | 基準値 |
| `paced` | マイペース型 | 基準値 × 0.5 |

- 基準値は、期限・現在のレベル・目標の大きさ・使える時間・他のタスク・希望を考慮できる構造にする
- 各候補には、週あたりの目標時間、想定期間、負荷、特徴、メリット、注意点、理由を表示する
- 3候補を同等に比較できるように表示し、特定の候補をAIの推薦として過度に強調しない
- 利用者が1つを選び、時間を微調整して最終値を決定する

**受け入れ条件**：3候補が表示され、選択・時間の編集・確定ができ、選択結果がAPIへ正確に送信される。

### 6.4 Goal Handoff（F-04） 優先度S

ヒアリング完了時には、以下のような正規化済みデータを Planning Engine へ渡す。会話履歴そのものは渡さない。

```json
{
  "goals": [
    {
      "task_name": "TOEIC学習",
      "target_hours_per_week": 6,
      "frequency": null,
      "deadline": null,
      "priority": "medium",
      "conditions": [],
      "user_selected_plan": "balanced"
    }
  ],
  "user_preferences": {
    "preferred_daily_limit": null,
    "preferred_days": [],
    "avoid_days": []
  },
  "constraints": {
    "fixed_schedule_required": true
  }
}
```

存在しない情報は推測せず、`null` または空配列として扱う。user_id はサーバー側で付与する。

### 6.5 固定予定・場所・移動時間（F-05） 優先度A

#### 6.5.1 固定予定

授業、アルバイト、約束、食事、睡眠など、時間が決まっている予定。Planning Engine は固定予定を変更しない。

各固定予定は、タイトル、種類、開始・終了日時、場所、繰り返し（毎週／なし）を持つ。

#### 6.5.2 場所

利用者がよく行く場所（自宅、大学、アルバイト先など）を登録する。各場所は名前と住所を持つ。

#### 6.5.3 移動時間

- 場所と場所の間の移動時間を、利用者が登録する「移動時間表」で管理する（MVPでは地図APIは使わない）
- 移動時間は所要分数と手段（徒歩・電車・バスなど）を持つ
- Planning Engine は、場所が異なる予定・タスクの間に移動時間を確保する
- 移動時間はタイムライン上に「移動」として表示する
- 移動中は原則としてタスクを配置しない（将来、移動中にできる軽作業の配置を検討する）

**受け入れ条件**：場所が異なる2つの予定の間に、移動時間表どおりの「移動」が必ず入っている。移動時間が確保できない配置は Validator がエラーにする。

### 6.6 タスク管理（F-06） 優先度A

利用者はタスクを登録・編集・削除できる。各タスクは以下の属性を持つ。

- タスク名
- 締切（なしも可）
- 所要時間・残り時間
- 重要度
- 集中力要求度
- 分割可能性
- 中断しやすさ
- バッファ適性
- 関連する目標（なしも可）
- 状態（未着手・進行中・完了）

MVPでは画面上の登録UIが間に合わない場合、seedデータで用意する。自然言語によるタスク登録は優先度Bとする。

目標（`goal_id`）に紐づく継続タスク（締切なし）は、所要時間・残り時間を次のとおり読み替える。

- 所要時間（`estimated_minutes`）：1回あたりの標準時間
- 残り時間（`remaining_minutes`）：今週その目標で残っている時間。同じ `goal_id` のタスクで共有する値で、目標の週あたり目標時間（`target_hours_per_week` × 60）から今週すでに実施した分を引いたもの

### 6.7 デイリーチェックイン（F-07） 優先度A

毎日、利用者の状態を簡単に入力できるようにする。

- 今日の気分
- 疲労度
- 集中できそうか
- 今日やりたいこと
- 今日やりたくないこと・避けたいこと

入力方法は選択式だけに限定せず、自然言語にも対応する（例：「今日はちょっと疲れてるから軽めにしたい」）。

### 6.8 スケジュール生成（Planning Engine）（F-08） 優先度S

#### 6.8.1 生成単位

- スケジュールは **今週（月曜〜日曜）の計画** として生成し、日ごとの計画（DailyPlan）の集まりとして保存する
- 過去の時間には新しくタスクを配置しない
- 「今日の予定」はその週の計画のうち今日の分を表示する

#### 6.8.2 処理順

```text
1. Validate（入力検証）
2. Fixed Events（固定予定の取得）
3. Sleep（睡眠の取得）
4. Travel（移動時間の確保）
5. Free Slots（空き時間の計算）
6. Hard Constraints（絶対条件の確認）
7. Task Priority（優先度計算）
8. Task × Slot Fit（適合度計算）
9. Buffer（バッファ確保）
10. Candidate Generation（3案生成）
11. Score（評価）
12. Validator（妥当性検証）
13. Return 3 Candidates
```

同じ入力からは同じ結果が出る（決定論的である）こと。

#### 6.8.3 絶対条件（Hard Constraint）

- 開始 < 終了
- 予定同士が重ならない
- 固定予定を侵食しない
- 睡眠を侵食しない
- 場所が異なる予定の間に移動時間がある
- 締切を過ぎて配置しない
- バッファが最低量以上ある
- 1日の作業時間が上限を超えない
- 過去の時間に新規配置しない

#### 6.8.4 スケジュール3案

| 内部名 | 表示名 | 方針 |
|---|---|---|
| `intensive` | 集中プラン | 重要タスクの達成を重視 |
| `balanced` | バランスプラン | タスク・バッファ・自由時間・コントロール感を均衡 |
| `relaxed` | ゆとりプラン | バッファ・自由時間・疲労状態への適合を重視 |

- **3案の違いを説明文だけにしてはいけない。** 実際の配置・タスク量・バッファ量・自由時間が変わること
- 3案とも、利用者が確定した目標（例：TOEIC週6時間）を勝手に減らさない。違いは、締切タスクの前倒し度合い、締切のないタスクの量、バッファ・自由時間の量で表す
- 3案すべて Validator を通す

各案は比較用に以下を持つ。

- タスク時間の合計
- バッファ時間の合計
- 自由時間の合計
- 移動時間の合計
- 目標に使う時間の合計
- 締切タスクの数
- 過密かどうか
- 説明文

#### 6.8.5 Validator

以下を検証し、真偽値だけでなくエラーの一覧を返す。

- 開始 ≥ 終了
- 予定の重複
- 固定予定の侵食
- 睡眠の侵食
- 移動時間の不足
- 締切違反
- バッファ不足
- 1日の作業時間の超過
- 不正なID

```json
{
  "valid": false,
  "errors": [
    { "code": "FIXED_EVENT_OVERLAP", "item_id": "...", "message": "..." }
  ]
}
```

**受け入れ条件**：同じ入力から3案が生成され、3案の中身（配置・量）が異なり、すべて Validator を通る。

### 6.9 バッファ（F-09） 優先度S

#### 6.9.1 定義

バッファとは、予定と予定の間に確保する余白時間を指す。単純な「何もしない時間」ではなく、以下の役割を持つ。

- 予定の遅延を吸収する
- 移動や準備の時間を確保する
- 疲労を回復する
- 予定変更に対応する
- 心理的な余裕を確保する
- 短時間で完了できるタスクを処理する

#### 6.9.2 空き時間をすべてタスクで埋めない

空き時間を見つけたからといって、必ずタスクを割り当てるわけではない。30分の空きがある場合でも、「25分の軽いタスク＋5分の余白」「15分の軽いタスク＋15分の自由時間」「30分すべて休憩」のように、利用者の状態によって異なる判断をする。休むことも計画上の正当な選択肢として扱う。

#### 6.9.3 バッファに適したタスク

短時間で完了できる、中断しても問題が少ない、高い集中力を必要としない、分割可能、開始・終了時間の自由度が高い、予定変更時の損失が小さい、心理的負担が小さい、といった特徴を持つもの。

例：メール確認、企業情報の軽い確認、授業資料の整理、ファイル整理、短時間の復習、単語学習、簡単な調査、タスクの整理

#### 6.9.4 バッファに向かないタスク

高い集中力が必要、中断による損失が大きい、長時間の連続作業が必要、締切直前で失敗リスクが高い、着手までの準備が大きい、心理的負担が大きい、といった特徴を持つもの。

例：本格的なプログラミング、重要なESの作成、長時間のレポート執筆、重要なプレゼン資料の作成、高度な問題演習

#### 6.9.5 状態による調整

| 状態 | 調整 |
|---|---|
| 疲労度が高い | 軽いタスクまたは休憩 |
| 集中できそう | 短時間の集中タスク |
| 予定が詰まっている | 余白を多めに残す |
| 締切が近い | バッファの一部をタスクに利用する |

#### 6.9.6 締切あり・なしタスクの扱い

締切のあるタスク（ES提出、レポート、授業課題など）は、締切までの残り時間や必要作業量を考慮して優先度を上げる。締切のないタスク（TOEIC、ケース面接対策、企業研究、プログラミング学習など）は、毎日すべてを消化しようとせず、余裕のある時間やバッファに適したタイミングで少しずつ進める。

### 6.10 今日のタイムライン（F-10） 優先度S

- 選択した計画のうち今日の分を、開始時刻順に表示する（DBの保存順ではなく開始時刻で並べる）
- 項目の種類（固定予定・移動・タスク・バッファ・自由時間・睡眠）を色や形で区別する
- 現在時刻を表示する
- 必要に応じて「なぜこの計画なのか」の理由を表示する
- ローディング・空・エラーの状態を用意する

### 6.11 カレンダー表示（F-11） 優先度A

選択した計画と固定予定を、月・週・日の3つの表示で確認できる。MVPでは**閲覧のみ**とし、ドラッグによる移動などの編集機能は作らない。

| 表示 | 内容 |
|---|---|
| 月 | 1か月のグリッド。各日に予定の有無・締切・計画の量を小さく表示。日付をタップすると日表示へ |
| 週 | 月曜〜日曜の7日分。各日の予定をブロックで表示。日をタップすると日表示へ |
| 日 | 1日のタイムライン（今日のタイムラインと同じ表示）。前日・翌日へ移動できる |

- 計画が作られていない期間は、固定予定と締切のみ表示する
- スマートフォンの画面幅で読めることを優先し、情報を詰め込みすぎない

### 6.12 再計画（F-12） 優先度A（Demo Pathに含む）

#### 6.12.1 自然言語による再計画

利用者は予定変更を自然な文章で伝えられる。

例：「今日は疲れた」「18時から予定が入った」「今日はもう勉強したくない」「このタスクを明日に回したい」「今から30分だけ何かやりたい」

LLMは発言から**意図（Replanning Intent）だけ**を抽出し、配置は Planning Engine が行う。

```json
{
  "type": "state_change",
  "fatigue": "high",
  "task_changes": [],
  "new_fixed_events": [],
  "preference_changes": []
}
```

#### 6.12.2 変更してよいもの・いけないもの

| 変更可能 | 変更禁止 |
|---|---|
| 未着手のタスク | 完了済みの項目 |
| 任意（Optional）のタスク | ロックされた項目 |
| バッファ | 固定予定 |
| 自由時間 | 睡眠 |
| | 締切 |
| | 目標 |

#### 6.12.3 成立しない場合の回復手順

```text
1. 必須タスク・締切タスクを残す
2. 任意タスクを削減する
3. バッファを最低量まで調整する
4. それでも不可能なら、利用者へ理由と必要な変更を説明する
```

睡眠・固定予定・締切を勝手に壊さない。

#### 6.12.4 結果の提示と確定

- 変更前（Before）と変更後（After）を並べて表示し、変更された項目だけを強調する
- 各変更に理由を添える（例：「疲労度が高いため、集中力が必要なESの下書きを水曜に移動しました。締切（10/12）には間に合います」）
- 今日以外の日に影響がある場合は、その内容も表示する
- 利用者が「この計画にする」を押すまで確定しない

#### 6.12.5 予定変更を失敗として扱わない

「今日は疲れているため、TOEICを明日に回す」という判断は、利用者が自分の状態に合わせて時間をコントロールした結果である。無計画による予定崩壊と、利用者の意思に基づく意図的な再計画を区別し、後者を否定的に表示しない。

### 6.13 判断理由の説明（F-13） 優先度S

AIが予定を作った場合、必要に応じて理由を説明できるようにする。

例：「ESを今日入れたのは締切が近いためです」「30分の空き時間には、15分で完了できるタスクを入れました」「今日は疲労度が高いため、集中力が必要なタスクを減らしています」

説明文の生成はLLMが担当してよいが、説明の根拠（どのルールで配置したか）は Planning Engine の結果に基づくこと。

## 7. Planning Engine の設計方針

### 7.1 理論的基盤

本システムの予定最適化では、「1日にできるだけ多くのタスクを詰め込むこと」を目的としない。

井邑・塚脇の研究では、時間管理が時間コントロール感と関連し、時間コントロール感が人生満足度と関連することが示されている。また、「時間の活用」は積極的な他者関係とも関連している。

この知見を応用し、最適化の目標を **「タスク消化量の最大化」ではなく、「利用者が自分の時間をコントロールできていると感じられる状態を作ること」** と定義する。

スケジュールを \(S\)、時間コントロール感を \(C(S)\) とすると、

\[
C(S)=w_1E(S)+w_2A(S)+w_3F(S)-w_4D(S)
\]

- \(E(S)\)：時間見積もりの正確性
- \(A(S)\)：時間の適切な活用
- \(F(S)\)：利用者の意思・状態との適合度
- \(D(S)\)：無計画性・過密状態・締切直前への集中などによる負担

予定全体の効用を

\[
U(S)=\alpha P(S)+\beta C(S)+\gamma R(S)+\delta B(S)-\lambda O(S)
\]

- \(P(S)\)：重要タスクの達成度
- \(C(S)\)：時間コントロール感
- \(R(S)\)：他者との関係や本人が大切にする時間の確保
- \(B(S)\)：バッファによる余裕・予定変更耐性
- \(O(S)\)：過密スケジュールによる負荷

とし、Planning Engine は \(\max_S U(S)\) を基本的な最適化目標とする。

### 7.2 時間の内訳とバッファ

1日の利用可能時間（睡眠を除く）を \(T\) とし、

\[
T=T_s+T_m+T_b+T_f
\]

- \(T_s\)：タスク・予定に使用する時間
- \(T_m\)：移動時間
- \(T_b\)：バッファ時間
- \(T_f\)：自由時間・休憩時間

バッファには最低量を設定し \(T_b\geq B_{\min}\) を基本制約とする。詰め込みすぎには過密度ペナルティを設定する。

\[
O(S)=\max(0,\ T_s-T_{\mathrm{comfortable}})^2
\]

タスクを追加するほど単純に効用が上がるのではなく、無理なく処理できる範囲を超えるとペナルティが大きくなる。

### 7.3 タスクと時間帯の適合度

タスク \(i\) を時間帯 \(t\) に配置する適合度を

\[
Fit(i,t)=b_i\times m_i(M,F,K)\times g(\Delta t)
\]

- \(b_i\)：タスクのバッファ適性
- \(m_i(M,F,K)\)：気分 \(M\)、疲労度 \(F\)、集中可能度 \(K\) との適合度
- \(g(\Delta t)\)：空き時間の長さ \(\Delta t\) との適合度

バッファ適性は

\[
b_i=w_sS_i+w_iI_i+w_dD_i+w_lL_i
\]

- \(S_i\)：短時間で完了しやすい
- \(I_i\)：中断しやすい
- \(D_i\)：分割しやすい
- \(L_i\)：低い集中力でも実行しやすい

評価要素には、所要時間、時間帯、集中力、認知負荷、分割可能性、中断しやすさ、チェックインの状態を用いる。

### 7.4 タスクの優先度

\[
W_i=\alpha P_i+\beta D_i+\gamma U_i+\delta W_i^{user}
\]

- \(P_i\)：重要度
- \(D_i\)：締切による緊急度
- \(U_i\)：未完了状態による優先度
- \(W_i^{user}\)：利用者が「今日やりたい」と感じている度合い

締切ありのタスクは残日数・残作業量・重要度を、締切なしのタスクは希望度・継続性・目標との差・最近の実施状況を用いる。優先度関数は「どこに置くか」を決めず、優先度だけを返す。

### 7.5 スケジュールの評価

\[
\begin{aligned}
Score ={}& \alpha\,DeadlineScore + \beta\,UserIntentScore + \gamma\,TaskFitScore + \delta\,BufferFitScore \\
&+ \varepsilon\,ControlScore + \zeta\,ProgressScore + \eta\,SocialTimeScore - \lambda\,OverloadPenalty
\end{aligned}
\]

係数はすべて設定ファイルで変更できるようにする。

### 7.6 他者との関係を含める

友人、家族、仕事仲間などとの時間を単なる空き時間として扱わない。

\[
R(S)=\sum_j v_j y_j
\]

- \(v_j\)：本人にとってのその時間の価値
- \(y_j\)：その時間が確保されたか

## 8. データ要件

### 8.1 主要なデータ

| データ | 内容 |
|---|---|
| users / user_preferences | 利用者と生活リズム（睡眠時間、1日の作業上限など） |
| locations | 場所（名前、住所、種類） |
| travel_times | 場所間の移動時間（出発地、到着地、分数、手段） |
| fixed_events | 固定予定（種類、場所、日時、繰り返し） |
| goals | 目標（Goal Handoff の内容） |
| tasks | タスク（6.6の属性） |
| daily_checkins | デイリーチェックイン |
| interview_sessions | ヒアリングの状態と会話 |
| weekly_plans | 週の計画（スケジュール3案と選択結果） |
| daily_plans / daily_plan_items | 日ごとの計画とその項目 |

すべてのデータは user_id を持ち、Supabase の RLS で本人のデータにしかアクセスできないようにする。

### 8.2 データの約束

| 項目 | ルール |
|---|---|
| 命名 | APIのJSON・Zodスキーマ・DBの列名は **snake_case**（例：`task_name`、`start_at`） |
| 日時 | ISO 8601形式・日本時間のオフセット付き（例：`2026-10-05T18:00:00+09:00`） |
| 日付 | `YYYY-MM-DD`（例：`2026-10-05`） |
| ID | 文字列（DBではUUID、モックでは読みやすい文字列でもよい） |
| 不明な値 | `null` または空配列。推測で埋めない |
| 候補の名前 | 目標時間は `intensive / balanced / paced`、スケジュールは `intensive / balanced / relaxed`。画面の表示名は6.3・6.8.4の表のとおり |
| 型の正 | `lib/schemas.ts` の Zod スキーマを唯一の正とし、TypeScript の型はそこから生成する |

## 11. 絶対に守ること

- LLMに最終スケジュールを生成させない
- 不明情報を推測しない
- 目標を勝手に変更しない
- ヒアリング直後に自動でスケジュールを生成しない
- 固定予定を変更しない
- 完了済み・ロック済みの項目を変更しない
- 睡眠を削らない
- 移動時間を削らない
- 空き時間を全部埋めない
- 3案の違いを説明文だけにしない
- 利用者の確認なしに再計画を確定しない
- UIの作り込みでバックエンドの統合を遅らせない
- 新機能の追加より Demo Path を優先する

## 12. 将来の機能（MVP後）

### 12.1 月間レビュー

長期目標、今後の方向性、優先したいこと、現在の方針、大きな方針変更を扱う（例：「就職活動を優先する」「資格取得を重視する」「大学の課題と就職活動を両立する」）。

### 12.2 週間レビュー

月間方針を具体化する。今週の重要タスク、タスク量、優先順位、スケジュール上の問題、前週からの調整を扱い、大きな方向転換はせず細かな調整を中心に行う。

### 12.3 利用者からの修正の学習

利用者がAIの提案を変更した場合、その変更を今後の計画に利用できる情報として蓄積する（例：朝は集中しにくい、30分以内のタスクなら取り組みやすい、疲れている日は勉強量を減らしたい）。ただし行動を過度に固定化せず、参考情報として利用する。

### 12.4 その他

Google Calendar連携、自然言語によるタスク登録、アルバイトシフト管理、地図APIによる移動時間の自動計算、移動中にできる軽作業の配置。

## 13. 成功条件と評価指標

### 13.1 成功条件

単純なタスク消化率だけでは評価しない。

- タスク登録にかかる手間が減る
- 計画を考える時間が減る
- 予定変更時の修正負担が減る
- 予定の詰め込みすぎが減る
- バッファと移動時間が確保される
- 利用者の状態に合ったタスクが選ばれる
- 「今日は何をすればいいか」を考える負担が減る
- AIの提案を簡単に修正できる
- 利用者が自分の意思で計画を調整できる

### 13.2 ヒアリングのUX評価指標

目標設定までの入力回数、目標時間決定までの負担、3候補からの選択率、提案後の修正回数、ヒアリング離脱率、ヒアリング完了率、スケジュール生成への遷移率、利用者が「自分で決めた」と感じる度合い、目標設定後の再修正率。

## 14. 人間側で深掘りする論点

MVPの実装とは別に、チームで議論を続ける論点。

**UX**：何を入力しなくてもよい状態が理想か／どこまでAIに判断を任せるか／AIが勝手に決めてよい範囲と確認が必要な範囲／自動化と「自分で決めている感覚」のバランス／「便利」と「勝手に決められる」の境界／入力疲れが発生しないUX／提案を拒否・変更する操作負担

**バッファ**：どの程度確保するか／バッファと自由時間の区別／何分以上の空きならタスクを入れるか／締切の近さによってどこまで削るか／中断しやすさ・心理的負担の評価方法／休むことを正当な選択肢としてどう扱うか

**移動**：移動時間の前後にどの程度の余裕を持たせるか／移動中にできる作業をどう扱うか
