# 本番化ロードマップ

## モックと本番の境界

| 領域 | モック | 本番 |
|---|---|---|
| データ | `mocks/` の固定ペルソナ・固定タスク・固定予定・固定プラン | 認証済み利用者の入力と永続化データ |
| API | `app/api/` の既存Route Handlerは `lib/mock/` と固定データを使う | 認証・入力検証・Domain Service・Repositoryを通す。本番用の切替方法と認証境界が決まるまでモックAPIを変更しない |
| 計画 | `lib/mock/plans.ts` が固定3案を返す | `lib/planning-engine/` が明示された入力から候補を計算する |
| デモ制御 | `lib/mock/` の時刻変更・リセット | 本番から到達できない |

既存のモックAPIとデモデータはデモ経路として維持する。画面表示やモック完了を、本番の認証・保存・AI・計画生成が動く根拠にしない。

## 実装順

1. **利用可能時間の算出（着手）**：日内の稼働範囲から睡眠・固定予定などのブロックを差し引く純粋関数を用意する。`lib/planning-engine/availability.ts` は分単位の明示入力だけを受け取り、`mocks/` やモックAPIに依存しない。呼び出し側でAsia/Tokyoの日付・繰り返し予定を日内範囲へ正規化する。
2. **本人データの保存**：認証方式・セッション、SupabaseのテーブルとRLS、所有者の決め方、更新競合・計画版を決め、利用者自身のタスクと固定予定を保存・取得する。
3. **計画候補の生成**：保存済みタスク・目標・設定・固定予定をPlanning Engineへ渡す。数学モデルにある評価指標・候補方向を実装可能な入力と係数に確定し、ハード制約の検証を通った3案だけを返す。
4. **選択と予定表示**：選択した計画を永続化し、今日・日週月表示から同じ利用者の計画を取得する。
5. **対話と再計画**：LLMの送信範囲・構造化出力・費用上限を定めてヒアリングへ接続する。再計画は提案と確定を分け、計画版を照合して保存する。
6. **タスク編集・チェックイン**：CRUDの削除影響と、チェックインの入力項目・保存期間・計画への反映を定めて追加する。

## 未決事項

- 認証プロバイダーとログイン体験。READMEはSupabaseを予定しているが、機能設計では認証方式・セッション・認可が未決。
- 永続化前に必要なER図、RLS、所有者、削除・履歴、計画版、バックアップ、ログの個人情報方針。
- Planning Engineの探索・評価は数学モデルに方向性がある一方、入力の確定方法、係数、性能上限、候補の多様性判定が未確定。
- タスクCRUD、チェックイン、設定編集の操作と既存計画への影響。

これらの値や方針は実装者が推測で固定しない。仕様が決まるまでは、モックから本番データを生成したり、固定データを本番入力として流用したりしない。
