# モック起点の機能要件・詳細設計書

## 0. この文書の使い方

### 0.1 目的

モックの画面・操作を出発点に、利用者ができること（機能要件）、画面からAPI・業務処理・データまでの流れ（詳細設計）、受け入れ条件を一続きで記録する。機能を追加・変更するときも、既存仕様との対応を追える状態を保つ。

本書は既存仕様を置き換えず、画面単位と機能単位の対応、実装設計、受け入れ条件を補う。

| 資料 | 正とする内容 |
|---|---|
| docs/requirements.md | 製品としての機能要件、利用者保護の原則、MVPの範囲 |
| docs/mock-spec.md | モックの画面遷移、表示内容、API契約、デモデータ |
| docs/design-spec.md | 見た目、画面上の表示名、色、部品 |
| docs/AI秘書_PlanningEngine_3候補生成_数学モデル.md | Planning Engineの数学モデル案。requirements.mdの制約に沿う実装の参考 |
| docs/requirements_final_complete.md | 旧版の参考資料。requirements.md と食い違う場合は現行の requirements.md を優先 |
| lib/schemas.ts | 実装時のAPI入出力とデータ形状 |
| 本書 | 要件・モック・実装の対応、機能ごとの詳細設計、追加時の記入方法 |

内容が食い違う場合は、機能の目的と制約は docs/requirements.md、モックの動作は docs/mock-spec.md、見た目と言葉づかいは docs/design-spec.md を優先する。本書だけで既存の仕様を変更しない。未決事項は推測で確定せず、11章に記録してチームで決める。

### 0.2 状態の表記

| 状態 | 意味 |
|---|---|
| モック実装 | 画面とモックAPIで一連の動きを確認できる。実サービスの認証・LLM・DB・最適化を意味しない |
| 一部実装 | 表示や読み取りなど一部の経路だけがある。未実装の操作を明記する |
| 要件のみ | requirements.md に目的・要件があるが、現在のモックに画面や操作がない |
| 将来 | MVP後に検討する。実装済みとして扱わない |
| 未決 | 判断材料が足りず、実装前に決定が必要 |

### 0.3 IDと変更の追跡

- 機能IDは docs/requirements.md の F-01〜F-13 を継続して使い、既存IDを再利用・振り直ししない。
- 新しい独立機能を追加するときは F-14 以降を採番し、先に requirements.md の機能要件へ追記する。
- 本書の設計項目は DS-01 以降、機能の受け入れ条件は AC-Fxx-01、横断条件は AC-API-01 等、手動シナリオは SC-01 の形式で採番する。廃止したIDも別の意味に再利用しない。
- 画面、API、スキーマ、データ、受け入れ条件の変更は同じ差分で相互参照を更新する。
- 「モックに見える」ことを機能完成の根拠にせず、0.2の状態と受け入れ条件を明記する。

## 1. 対象範囲と利用者の流れ

### 1.1 対象

対象画面は /login、/interview、/plans、/today、/replan、/calendar、/settings。主な利用者は本人、外部の技術境界はブラウザ、Next.js Route Handler、Planning Engine、将来の永続化層とする。

### 1.2 デモの主経路

~~~mermaid

  B --> C["目標を確認"]
  C -->|"利用者が押す"| D["スケジュール作成"]
~~~

## 2. システム境界と設計方針

### 2.1 現在と将来のデータ経路

~~~mermaid
flowchart LR
  U["画面<br/>app/・components/"] --> C["lib/api.ts<br/>HTTPクライアント"]
  C --> V["lib/schemas.ts<br/>Zod契約"]
  C --> R["app/api/<br/>Route Handler"]
  R --> M["lib/mock/<br/>モック状態・処理"]
  M --> D["mocks/<br/>固定データ"]
  R -. "本番へ差し替え" .-> S["Domain Service"]
  S --> P["Repository"]
  P --> DB["永続化層"]
~~~

現在の実装では画面が lib/api.ts を経由し、Route Handler が lib/mock と mocks のデータを使う。画面から mocks を直接 import しない。将来の Domain Service / Repository は拡張案であり、配置を追加するときに重複する責務を持つファイルを作らない。

### 2.2 責務

| 層 | 責務 | 禁止・境界 |
|---|---|---|
| 画面・共通部品 | 入力、表示、選択、読み込み・空・エラー状態、画面遷移 | 計画配置や優先度の決定を持たない。モックデータを直接参照しない |
| lib/api.ts | 型付きのHTTP呼び出し、タイムアウトと通信エラーの扱い、レスポンス検証 | 業務判断を置かない |
| app/api | リクエストの受け口、入力検証、認証境界、アプリケーション処理の呼び出し、レスポンス検証 | LLMにスケジュール配置を委ねない |
| Domain Service（本番化時） | ヒアリング状態遷移、計画生成、再計画等の業務規則 | UIやデータベースの詳細に依存しない |
| Planning Engine | 空き時間、制約、優先度、適合度、候補生成、検証 | 固定予定・睡眠・締切・確定目標・完了済み・ロック済みを勝手に変更しない |
| Repository / 永続化（本番化時） | user_id で分離した保存・取得 | クライアントの user_id を信用しない |
| lib/mock / mocks | デモ用の状態管理と固定データ | 本番のLLMやSupabaseを呼ばない |

### 2.3 共通の契約

- APIのJSON、Zodスキーマ、DB列は snake_case とする。日時は +09:00 付きISO 8601、日付は YYYY-MM-DD。
- データ形状の正は lib/schemas.ts とし、同じ型やZodスキーマを別ファイルに重複定義しない。
- 不明値は null または空配列で表し、会話や画面から推測で補わない。
- 画面からデータを取得・更新するときは lib/api.ts の関数を使う。
- Route Handlerは受信値を検証し、返却前に対応するレスポンススキーマを parse する。
- 本番化でモック実装を差し替える場合も、既存のAPIパスと入出力を維持する。変更が必要なら先に requirements.md、schemas.ts、本書を一緒に更新する。
- UIはスマートフォン縦画面（幅375〜430px）を基準とし、主要タップ領域を44px以上にする。

## 4. 画面・APIの機能要件

ここに記す条件はモックに対する追加の受け入れ条件であり、requirements.md の受け入れ条件を狭めない。

### 4.1 ログインとヒアリング（F-01〜F-04）

- AC-F01-01：ログイン操作でモックログインAPIを呼び、成功後に目標相談へ進む。これは認証済みアクセスを証明しない。
- AC-F02-01：自由入力とクイックリプライのどちらでも発言でき、二重送信を防ぐ。失敗時は入力内容を失わず再試行できる。
- AC-F02-02：ヒアリング状態の遷移をAPI応答に従って表示し、完了しただけでは計画生成APIを呼ばない。
- AC-F03-01：3候補の比較に必要な時間、負荷、期間、特徴、利点、注意点、理由を同じ構成で表示する。
- AC-F03-02：選択後の時間調整は1〜15時間、0.5時間単位に制限し、選択結果を送信する。
- AC-F04-01：利用者の確定操作前に、goal を確定済みとして扱わない。未提供の値は null または空配列とする。

### 4.2 計画候補と今日の予定（F-08〜F-10、F-13）

- AC-F08-01：「スケジュール作成」の操作でのみ生成APIを呼ぶ。成功時は3候補を受け取り、失敗時は再試行できる。
- AC-F08-02：候補は利用者が比較できる実際の配置差を持ち、全案が制約検証を通る。現在のモック候補は固定データであり、生成アルゴリズムの合格根拠にはしない。
- AC-F08-03：計画の確定は候補の選択操作でのみ行う。選択した active_plan_id を画面遷移後にも読み取れる。
- AC-F09-01：タスク、移動、バッファ、自由時間、固定予定、睡眠を異なる種別として表示・集計する。
- AC-F09-02：空き時間をすべて作業で埋めず、利用者の状態に応じた余白を保持する。
- AC-F10-01：今日の項目は start_at の昇順で表示し、同時刻項目の順序規則もデータ契約に定める。
- AC-F10-02：タスクまたはバッファの詳細で、表示可能な場所・締切・候補タスク・reason を確認できる。存在しない値は推測して表示しない。
- AC-F10-03：読み込み中、空、失敗を区別し、失敗時に再取得できる。
- AC-F13-01：各説明を対象項目・計画案と関連付け、単なる一般文で配置根拠を代替しない。

### 4.3 予定変更（F-12）

- AC-F12-01：入力を送信すると、対応可能な場合は変更前・変更後・理由・他日への影響を含む提案を表示する。未対応入力は理由を返し、予定を変更しない。
- AC-F12-02：提案中は確定操作前に保存データを変更しない。確定操作でのみ提案を適用する。
- AC-F12-03：取消時は提案を破棄し、元の計画を維持する。
- AC-F12-04：固定予定、睡眠、締切、目標、完了済み・ロック済み項目を移動・削除しない。
- AC-F12-05：変更が複数日に波及する場合、利用者が確定する前に全対象日と影響理由を見られる。

### 4.4 カレンダー・設定・チェックイン（F-05〜F-07、F-11）

- AC-F11-01：月・週・日は同じ選択中の計画と固定予定を参照し、日付を切り替えても対象日が一致する。表示だけで予定を変更しない。
- AC-F05-01：設定画面の読み取り表示と更新操作を区別する。編集を追加するまでは表示のみとする。
- AC-F06-01：タスク詳細は取得済みの Task データを使う。登録・編集・削除ボタンが存在する前提で設計しない。
- AC-F07-01：チェックインの入力項目、状態遷移、保存期間、再計画・計画生成への影響を決め、F-07の受け入れ条件と画面/API設計を同時に更新する。現在のモックから未定義の挙動を推測しない。

## 5. 詳細設計

### DS-01 共通のAPI・画面処理

1. 画面は hooks/use-api-data.ts またはイベントハンドラーから lib/api.ts の関数を呼ぶ。
2. lib/api.ts はHTTPメソッド・パス・入力を組み立て、応答を schemas.ts で検証する。タイムアウト、通信失敗、HTTP失敗は画面が扱える失敗として返す。
3. Route Handlerは入力を検証し、モック機能の場合は lib/mock/ に委譲する。レスポンスも返却前に検証する。
4. 画面は loading / success / empty / error を区別する。ユーザー操作に伴う送信中と失敗は対象操作の近くに表示する。
5. 新しいリクエストは、パス・メソッド・request/response schema・利用画面・失敗動作を同時に設計する。画面からの直接 fetch や mocks への直接参照を増やさない。

本番化では、認証済みユーザーをサーバー側で特定し、入力の user_id を権限判定に使わない。LLMの出力は構造化データとして検証し、最終的な予定配置を Planning Engine に渡す。

### DS-02 ヒアリングと目標（F-02〜F-04）

| 項目 | 設計 |
|---|---|
| 画面 | /interview。会話、クイックリプライ、目標時間3候補、確認、計画作成への導線 |
| API | POST /api/interview/start → POST /api/interview/message → POST /api/interview/confirm |
| 状態 | INTERVIEWING → CONFIRMING → COMPLETED → READY_FOR_PLANNING。READY_FOR_PLANNING から PLANNING へ進めるのは利用者が作成を選んだ場合のみ |
| 入力 | 発話 text または候補 selection の一方。選択案の編集値はスキーマで範囲・単位を検証 |
| 出力 | InterviewTurn、確定前の goal draft、確定応答。会話ログと Planning Engine に渡す構造化データを分ける |
| モックと本番 | モックは固定台本。本番の自然言語理解はサーバー側のLLMアダプターへ隔離し、対話状態・契約・承認境界を維持 |
| 失敗 | 不正な状態遷移は拒否する。通信失敗では現在の発言を保ち再試行可能にする |

### DS-03 計画候補の生成・選択（F-08、F-09）

**生成の入口**はヒアリングの確認とは別にする。利用者がスケジュール作成を選択した時点で、確定済みの goal と制約を入力として週の3案を生成する。

| 順序 | 処理 | 主な検証・出力 |
|---:|---|---|
| 1 | 入力と対象週を検証 | goal、preferences、tasks、fixed_events の整合性 |
| 2 | 固定予定・睡眠・場所を正規化 | 固定予定を不変条件として保持 |
| 3 | 移動時間を確保して空き時間を計算 | 移動不足を後続検証で検出可能にする |
| 4 | Hard Constraintを適用 | 重複、睡眠・固定予定侵食、締切、作業上限、過去時間 |
| 5 | タスク優先度・時間帯適合度を評価 | 優先度と時間帯のFitを別軸で扱う |
| 6 | タスク・バッファ・自由時間の候補配置 | 空き時間をすべて埋めない |
| 7 | 3方向の候補を生成し、多様性を評価 | 集中・バランス・ゆとりの配置と量に実差を持たせる |
| 8 | Validatorを実行 | 3案すべてが有効であること。違反時は候補を返さない |
| 9 | 候補と比較指標を返す | タスク、余白、自由時間、移動、目標時間、締切タスク等 |
| 10 | 利用者が案を選択 | 選択後に active_plan_id を更新 |

モックでは現在、mocks/plans/ の候補を返しており、上記の探索処理を実行していない。本番の生成責務は Planning Engine に置く。実装を拡張するときは lib/planning-engine/ 等の独立した境界に処理を分ける案を検討し、既存モックロジックと同じ計算を二重に持たない。

### DS-04 今日の予定と予定表（F-10、F-11、F-13）

- 今日画面と予定表の日表示は共通の DayView を使い、開始時刻順に同一の項目を表示する。
- 週表示は7日分の DayView、月表示は日ごとの要約を使う。未生成の期間は固定予定と締切だけを表示する。
- Timeline は予定種別・現在地／次の予定・締切・場所を表示し、詳細シートは存在するデータのみを表示する。
- カレンダーはMVPでは閲覧のみ。ドラッグ変更や独立した予定編集を追加する場合、権限・確定境界・Validatorを先に定義する。
- 表示用合計値はAPIの返却値か共有集計関数から得る。画面ごとにタスク時間や余白の定義を複製しない。

### DS-05 再計画（F-12）

1. POST /api/plans/replan は対象日・発言を受け、再計画意図を構造化する。本番では自然言語解釈と配置探索を別の責務にする。
2. Planning Engineは現在計画を読み取り、変更可能な未着手タスク・バッファ・自由時間だけを対象に提案を作る。固定予定等の不変条件を再検証する。
3. APIは ReplanProposal として Before、After、変更差分、理由、影響日、proposal_id を返す。提案の作成時点では現行計画を変更しない。
4. 利用者が確定したときだけ POST /api/plans/replan/accept を呼び、競合を再検証して適用する。取消は適用APIを呼ばず、状態を保持する。
5. 確定時には対象計画の版を照合し、提案作成後に計画が変わっていた場合は古い提案をそのまま適用しない。

現在のモックは「今日は疲れた」とその言い換えだけに固定対応する。対応外の発言は非対応応答を返し、候補提示・計画変更を行わない。版管理と同時更新の競合解決は本番化時に実装する。

### DS-06 ログイン、タスク、設定、チェックイン（F-01、F-05〜F-07）

| 項目 | 現在のモック | 本番化・拡張時に決めること |
|---|---|---|
| 認証 | 仮ログインAPIでデモ利用者を返す | 認証プロバイダー、セッション、認可、アカウント削除、データ分離 |
| タスク | GET /api/tasks と詳細表示。fixturesを使用 | CRUD、更新権限、削除時の計画・履歴との関係、監査 |
| 設定 | GET /api/settings。生活リズム・場所・移動時間・目標を表示 | 編集単位、検証、変更が既存計画へ与える影響、変更確認 |
| チェックイン | 現在のモック画面・APIなし | 入力項目、1日複数回の扱い、保存期間、履歴、計画生成への反映、未入力時の扱い |
| デモ制御 | 時刻変更とモックリセット | 開発・デモ環境に閉じ、本番経路から到達できないこと |

## 6. データと不変条件

### 6.1 ドメインデータの境界

docs/requirements.md 8章と lib/schemas.ts を正とする。設計上のデータ群は users / preferences、locations / travel_times、fixed_events、goals、tasks、daily_checkins、interview_sessions、weekly_plans、daily_plans / daily_plan_items。DBのテーブル構成は本書で先に固定せず、永続化実装前にER図・制約・インデックス・RLS方針を追記する。

### 6.2 変更禁止の不変条件

- 固定予定、睡眠、締切、確定済み目標、完了済み、ロック済み項目は利用者の確認なく変更しない。
- 計画候補や再計画提案は、利用者の選択・確定前は読み取り専用とする。
- 予定同士の重複、場所が異なる予定間の移動不足、締切超過、最低バッファ未満、1日の作業上限超過をValidatorで検出する。
- 予定の start_at は end_at より前とする。時刻比較と日付境界は Asia/Tokyo の仕様に従う。
- 不明な入力を黙って削除・補完せず、検証エラーか未指定値として返す。

### 6.3 本番永続化の設計項目

Supabase等を接続する前に、各レコードの所有者、更新競合、削除・履歴、計画版、RLS、バックアップ、個人情報を含むログ方針を決める。認証・永続化がモックにあるものとして扱わない。

## 9. 実装状況と仕様の空白

| 項目 | 現在の事実 | 次に実装する前に必要な判断 |
|---|---|---|
| 認証・ユーザー分離 | ログインはモック応答 | 認証方式、セッション、認可、RLS |
| LLM | モックAPIは呼び出さない | 送信データ、プロンプト、構造化出力schema、失敗・再試行、費用上限 |
| Planning Engine | 画面に表示する3案は固定データ | 入力契約、目的関数、探索方法、決定性、性能上限、Validator |
| チェックイン | F-07の要件はあるが画面・APIがない | UXと状態データから計画への反映規則 |
| タスク編集 | タスク参照のみ | 作成・更新・削除、繰り返し、締切と既存計画への影響 |
| 設定編集 | 設定は読み取りのみ | 設定変更時に現行計画を維持・再計算する条件 |
| API共通エラー | クライアントはHTTP失敗・タイムアウトを扱う | 本番APIのエラーschema、エラーコード、相関ID |
| 同時更新 | 単一メモリ状態のモック | 計画バージョン、競合検出、冪等性 |

決定が必要な項目を実装者の推測で埋めない。質問が必要な内容は docs/requirements.md の未決事項か本書11章に追記する。
